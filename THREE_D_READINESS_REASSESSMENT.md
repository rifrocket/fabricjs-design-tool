## Proven

Each claim below cites the chunk(s) that established it and the test(s) that currently enforce it — not an assertion from memory.

- **`RendererApi<TNode>` has two independent implementations.** `FabricRendererApi` (Chunk 2.2, wraps the real Fabric `Canvas`/`ViewportManager`/`SelectionManager`) and `MockRendererApi` (Chunk 9.2, `packages/core/src/testing/mockRendererApi.ts`, backed entirely by plain arrays/maps, zero Fabric import). Both satisfy the exact same `SceneApi & SelectionApi & ViewportApi & SerializationApi & LifecycleApi` contract.
- **Commands, `HistoryManager`, and `ObjectTypeRegistry` are genuinely generic, not just typed generically.** `AddObjectCommand`/`RemoveObjectCommand`/`SetPropertyCommand` (Chunks 3.2/3.3) and `ObjectTypeRegistry<TNode>` (Chunk 1.2) were exercised end-to-end against `MockRendererApi`/`MockNode` in Chunks 9.3/9.4 (`mockRendererApi.test.ts`, 16 tests), not just against `FabricObject`.
- **A real, already-shipped plugin's own authoring pattern works against a non-Fabric renderer**, for the parts of `EditorContext` that are actually generic (see the two gaps below for the parts that aren't). Chunk 9.5 ported `plugin-shapes-basic`'s exact `install(context) { registry.register(...) }` shape against `MockRendererApi`, including `addObjectOfType`, undo/redo, and a full round trip through `syncRendererToCanonicalPage`/`syncCanonicalPageToRenderer`.
- **A `CanonicalDocument` loads, saves, and migrates with zero renderer involvement, and survives a full destroy-and-recreate cycle.** `canonicalDocument.ts` (Chunk 6.1/6.2) has zero Fabric import, enforced by the `document-assets-no-renderer` dependency-cruiser rule (Chunk 0.3/6.5, `pnpm packages:depcruise` — currently 107 modules/424 dependencies, clean). Chunk 10.4's `documentLifecycle.test.ts` destroys every source `CanvasEngine`, round-trips the saved data through `loadCanonicalDocument()` with no engine alive anywhere, then recreates three pages via fresh engines byte-for-byte.
- **`DocumentSession` gives correct multi-page asset and (opt-in) history ownership**, validated both in isolation (Chunk 4.4) and inside real `plugin-pages` usage (Chunks 10.2/10.3, `PagesManager.sharedAssets.test.ts` / `PagesManager.sharedHistory.test.ts`) — a shared `AssetStore`/`HistoryManager` passed via `engineOptions` reaches every page's lazily-created engine with zero `PagesManager.ts` wiring changes, while the unopted-in default (independent per-page assets/history, `plugin-pages`' original design) is unaffected: its full 82/82 test suite (now 87/87 with the new tests) passes unmodified.
- **A single-page app can adopt `DocumentSession` + multi-page incrementally, with zero plugin code changes.** Chunk 10.5 migrated a plain `createEditor()` app running the real, unmodified `@rifrocket/fdt-plugin-shapes-basic` package into a `PagesManager`-managed multi-page document via the existing `seedFromDocument()` bridge, and confirmed the plugin still functions (not just installs without throwing) on both the adopted page and a newly added one.
- **Stage 8's migration acceptance bar is met.** A repo-wide grep for `getFabricCanvas()` (excluding test files, the method's own definition, comment-only lines, and `featureDocs.ts`'s two documentation-string literals) turns up 18 real invocation lines — 19 individual `.getFabricCanvas()` expressions, since one line invokes it twice — across 11 files; every one carries an explicit "why this stays" explanation citing `FUTURE_IMPLEMENTATION.md Chunk 8.3` and the specific Fabric-only concept involved (DOM `wrapperEl` structure, `calcOffset()`, prototype-patching render internals, `selection`/`evented` interactivity flags, etc.), either directly adjacent or as a file/function-level comment above — spot-checked directly against the current source in this pass, not assumed from an earlier stage's notes. (Corrected 2026-08-13: an earlier pass of this document reported "39 matches," which conflated raw grep line-hits — comments, the definition, doc-string literals — with genuine call sites; the undercount doesn't affect the substantive finding that every real site is explained.)
- **Existing single-page apps and existing plugin test suites are unaffected by any of this.** `pnpm packages:typecheck`, `pnpm packages:test`, `pnpm packages:build`, `pnpm packages:depcruise`, and `pnpm apps:build` were run green after every chunk in Stages 0–10, most recently after Stage 10's commit (33/33 packages typecheck, 42/42 test packages pass, depcruise clean, `apps/demo` builds). ## Not proven / still needed for real 3D

Nothing below is a defect in Stages 0–10's own stated scope — each item was either explicitly out of scope from the roadmap's own "Explicitly out of scope" section, or a gap first surfaced by Stage 9/10's validation work itself and deliberately left unfixed as a validation-only chunk shouldn't expand into an architecture change. Two of these (the `EditorContext` gaps) are genuine, previously-undocumented findings from this pass, not restatements of known limitations.

- **No real second renderer exists.** `MockRendererApi` proves the *interface* is implementable without Fabric; it does not prove the interface's *shape* is right for WebGL/Three.js/Babylon.js. In particular, `ViewportApi` (`getZoom`/`setZoom`/`pan`/`panTo`) is inherently 2D-shaped — no z-axis, no camera concept, no projection matrix — and `SelectionApi`'s flat "active nodes" list has no notion of raycasting/hit-testing in 3D space. A real 3D renderer will likely need its own capability interfaces (camera, lighting, materials) composed alongside — not instead of — a redesigned or narrowed `ViewportApi`/`SelectionApi`, exactly as the original plan anticipated but never attempted.
- **`EditorContext<TNode>.registry` is not actually generic over `TNode`, despite `EditorContext`'s own generic signature** (found in Chunk 9.5). `PluginRegistry.objectTypes` (`pluginRegistry.ts`) is hardcoded to `ObjectTypeRegistry<FabricObject>`. The literal pattern every shipped plugin uses today — `context.registry.objectTypes.register()` (e.g. `plugin-shapes-basic/src/plugin.ts`) — only ever type-checks against `FabricObject`. A real non-Fabric renderer plugin cannot reach a `TNode`-typed object registry through `context.registry` the way today's plugins do; Chunk 9.5's test worked around this with a second, separately-exposed `ObjectTypeRegistry<MockNode>` field, which is not itself a fix. Fixing this for real means widening `PluginRegistry` (and, by extension, its four other sub-registries: tools, panels, effects, exporters/importers) to be generic — a real design decision, not a mechanical change, and explicitly not attempted here.
- **`EditorContext<TNode>.use(plugin: EditorPlugin): void` is hardcoded to `EditorPlugin<CanvasEngine>`, regardless of `TNode`** (found in Chunk 9.5, confirmed via a real `TS2416`, not a hypothetical). `EditorPlugin<TContext = CanvasEngine>`'s own default type parameter means no `EditorContext` implementer other than the literal `CanvasEngine` class can satisfy that exact signature — Chunk 3.1's bivariance finding, which made `install(engine)`-shaped plugins compile against `EditorContext`, only works because every real plugin today targets the one concrete `CanvasEngine`; it does not generalize to a genuinely different context type (`FakeEditorContext` in Chunk 9.5's test could not `implements EditorContext<MockNode>` for this reason, and had to use its own self-consistent `use()` signature instead). A real second `EditorContext` implementation (for a real second renderer) would hit this immediately.
- **`resolveObjectTypeId`/`getObjectId` (`canonicalSceneSync.ts`'s default type/id resolution strategies) are inherently Fabric-specific**, not renderer-neutral. Chunk 9.5's widening of `syncRendererToCanonicalPage`/`syncCanonicalPageToRenderer` to `TNode extends SceneNode` (a real, scoped fix made in that chunk) made these strategies *injectable*, but did not make the *defaults* generic — a real non-Fabric renderer must always supply its own `resolveTypeId`/`getNodeId`, there is no renderer-neutral fallback.
- **`CanonicalNode.children` (nested nodes, e.g. Fabric groups) is declared but never populated.** Every sync path in Stages 5/6/9/10 is top-level-nodes-only, a limitation stated at each stage but never lifted.
- **`CanonicalPage.rendererId` is page-scoped, not node-scoped.** This allows different *pages* of one document to use different renderers (a Fabric page next to a future 3D page), which is real and tested (Chunk 10.4 asserts `rendererId === "fabric"` per page) — but it does not allow *mixing* 2D and 3D nodes on the *same* page. That remains a genuinely harder, unattempted problem.
- **`AssetStore` is deliberately minimal.** No dedup, no quotas, no eviction, no persistence integration, no remote asset management (Chunk 4.1's explicit scope). `plugin-local-storage`/`plugin-pages`' own persistence layer was never migrated to use `AssetStore`/`DocumentSession` by default — explicitly out of scope for the whole roadmap.
- **`ObjectTypeDefinition.serialize()`'s "portable properties" contract (Chunk 6.1) is documented, not enforced.** Nothing in the type system or at runtime catches a `serialize()` implementation that returns renderer-specific data instead of truly portable properties; the contract is a code-comment convention, verified only by the handful of `serialize`/`deserialize` implementations actually written for these tests (`round-trip-rect`, `mock-rect`).
- **`ViewportManager`/`SelectionManager`/`LayerManager`/`AlignmentManager`/`SnapEngine` remain entirely Fabric-typed internals**, wrapped by `FabricRendererApi` rather than made generic — explicitly out of scope for the whole roadmap from the start (see `FUTURE_IMPLEMENTATION.md`'s "Explicitly out of scope" section), and unchanged by anything in Stages 0–10.
- **`apps/npm-verify` (publish-and-real-install verification) does not exist on this branch** — the roadmap's own completion checklist includes an `apps/npm-verify` spot-check, but `ls apps/` on `version-5` shows only `demo` and `docs`. This checklist item is unverifiable in this repo state, not confirmed passing; it is not silently marked done.

## Recommendation

Do not begin 3D implementation next. The two `EditorContext` gaps found in Chunk 9.5 (a non-generic `PluginRegistry`, and `EditorPlugin`'s `CanvasEngine`-hardcoded default) are the actual blocker for a second real renderer's plugins to be authorable the same way Fabric plugins are today — a real 3D renderer effort should resolve those first (a scoped `EditorContext`/`PluginRegistry`/`EditorPlugin` design change, smaller than this whole roadmap but larger than anything attempted in a validation-only stage), then design the 3D-specific capability interfaces this document explicitly did not attempt, before writing any 3D object types or a Three.js/Babylon.js dependency.
